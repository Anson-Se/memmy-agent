# 插件安装与权限 PRD

## 一、这篇文档解决什么

Memmy 里有多个插件（文献综述、Office、法律等），它们对不同用户的开放程度不一样：有的所有人都能用，有的要登录才能用，有的还在内测、只给白名单用户用。

现在"谁能用、怎么安装"这些判断都写死在主程序里，每新增或调整一个插件都要改主程序。本方案让**每个插件自己携带这些规则**，主程序只负责按规则统一执行。

## 二、三个插件怎么开放


| 插件     | 代码来源                           | 怎么分发给用户      | 怎么安装    | 谁能用      |
| ------ | ------------------------------ | ------------ | ------- | -------- |
| 文献综述   | 插件仓库（Literature-Review-Plugin） | 运行时从插件仓库按需下载 | 登录后自动安装 | 登录用户     |
| Office | 各自插件仓库                         | 运行时从插件仓库按需下载 | 用户手动点安装 | 所有人      |
| 法律     | 各自插件仓库                         | 运行时从插件仓库按需下载 | 登录并开白后自动安装 | 登录且在内测白名单 |


> 说明：三个插件的代码都在各自插件仓库开发、打成安装包，这点相同；成品包**都不打进 App 安装包**，而是运行时由服务器按资格发放、按需下载。
>
> 为什么不打进安装包：**打进安装包 = 用户本地就有这份文件**（只做完整性校验、不加密，扒开安装包能拿到）。改为按需下载后，服务器能确保没资格的人根本拿不到包（法律插件对未开白用户不可见、不可下），公开安装包也不会变成免费下载源。需要说明的是：任何交付到客户端的插件，已登录/有资格的用户在本地仍可能扒出，真正需要保密的核心逻辑应放在服务端。

## 三、不同用户看到什么（示例）


| 用户        | 文献综述         | Office | 法律               |
| --------- | ------------ | ------ | ---------------- |
| 未登录       | 提示"去登录"      | 可安装    | 看不到（不存在于列表）      |
| 已登录、无内测资格 | 可用           | 可安装    | 看不到              |
| 已登录、有内测资格 | 可用           | 可安装    | 自动装好、可用，带"内测"标识和反馈入口 |


其他状态：插件还没发布可安装版本时显示"即将上线"。

> 官方模型说明：文献综述等插件**推荐使用 Memmy 官方模型**（效果更好），该说明写在**插件详情页**。对话内**不强制、不额外弹提示**，模型选择器保持可用，用户可自由切换到自己的模型（效果可能变差）。（服务端已能对用户自有模型的调用日志做加密，隐私顾虑已解决，因此无需强制官方模型。）

## 四、核心规则

**基本机制**

- **规则跟着插件走**：每个插件自己声明"怎么分发、怎么安装、谁能用"，主程序读取后决定对当前用户显示成什么样。
- **资格由服务器说了算**：是否登录、是否在白名单，都由服务器判定，本地改不了。内测插件的安装包也由服务器按资格发放——没资格的用户既看不到、也下载不到。

**安装与更新**

- **资格满足即自动安装**：文献综述（登录）、法律（登录且开白）在资格满足时自动下载装好，无需用户手动点；Office 面向所有人、并非人人都需要，保留手动安装。
- **自动安装绑定"资格刷新"，不是"登录动作"**："资格满足"是持续判定，不是登录那一刻的一次性检查。App 启动、打开插件面板 / 刷新、定时轮询或服务器下发资格变更时，都会重新校验；一旦发现资格**从无到有**（如先登录、后被开白）且用户未手动卸载过，就自动安装。因此"先登录、后开白"的用户**无需重新登录**，下次资格刷新时即自动装好。
- **默认自动升级**：插件默认自动升级，升级前重新确认资格。

**资格失效（退出登录、被移出白名单等）**

- **只影响"能不能用"，不影响"装没装"**：已安装的插件变为**不可用状态**（灰掉、界面提示"去登录"），但**文件保留、不卸载、不再更新**；进行中的任务允许跑完、不再新开。
- **恢复即用**：重新登录 / 恢复资格后立即可用、无需重新下载。真正删除文件的只有用户主动卸载（且卸载过的不会被自动装回）。

**可见性策略**

- **法律插件内测期完全隐藏**：没开白的用户看不到；以后想做用户转化，再切换成"可见但不可用 + 申请入口"，只需改插件侧配置，主程序不动。

## 五、代码分工

**三方各控制什么**

| 角色 | 控制什么 | 不做什么 |
|---|---|---|
| 插件仓库（每个插件一个） | 插件业务本身（功能、界面、技能、命令）；规则声明（怎么分发、怎么安装、谁能用、无资格时隐藏还是灰显）；打出安装包 | 不写"如何判定、如何停用"的通用逻辑 |
| 主仓库（memmy-agent） | 插件系统本体（加载、安装、启用、卸载、更新、运行）；通用判定与执行（读"插件声明+服务器资格"，算出并执行"看/装/用"）；受信任插件清单与下载包哈希校验 | 不为任何具体插件写死业务规则 |
| 服务器 | 判定并下发用户资格（登录、白名单）；按资格发放安装包；插件功能调用时二次校验兜底 | — |

**三个判断分别由谁控制**

| 判断 | 规则谁定 | 资格谁判 | 谁执行 |
|---|---|---|---|
| 能不能看到 | 插件（无资格时隐藏 / 灰显） | 服务器（登录、白名单） | 主程序决定是否渲染；服务器对无资格账号不发包 |
| 能不能安装 | 插件（谁能装、自动 / 手动） | 服务器 | 主程序发起安装；服务器按资格发包；后端安装时再校验 |
| 能不能用 | 插件（谁能用） | 服务器 | 主程序停用 / 放行；功能调用时服务端二次校验 |

一句话：**"看 / 装 / 用"三个判断，规则都在插件、资格都在服务器、执行都在主程序；主程序是通用裁判，只按规则和资格办事，不为哪个插件写死代码。**

## 六、落地步骤

1. 给插件的规则声明增加"怎么分发 / 怎么安装 / 谁能用"三项，默认所有人可用、手动安装，不影响现有插件。
2. 三个插件各自在插件仓库填好规则。
3. 服务器下发用户资格，对没资格的账号不发放安装包；主程序在安装、启用时校验资格。
4. 主程序改为按规则统一执行，删除写死的插件规则。
